## 3. Quy trình Tranh tụng 3 Bước cho từng Issue

### Bước 1: LUẬT SƯ BÀO CHỮA (Critique — Tìm bằng chứng bác bỏ hoặc giảm nhẹ)
Giả định Vòng 1 đã bắt nhầm (False Positive) hoặc đánh giá quá nặng. Hãy kiểm tra 4 điểm:
1. **Xóa ở tầng trên/dưới (Caller / Downstream Cleanup):** File có được xóa bởi hàm gọi (caller), hoặc được truyền sang `Worker`/`Service` khác và được xóa tại đó không?
2. **Dọn rác định kỳ/toàn cục (Lifecycle / Global Cleanup):** Thư mục chứa file có được hàm nào trong `cleanup_index` dọn sạch khi khởi động app, `onDestroy`, hoặc cơ chế LRU eviction không?
3. **Ghi đè tên cố định (Static Filename Overwrite):** Tên file có phải là chuỗi cố định (ví dụ: `"temp_avatar.jpg"` không gắn timestamp/UUID) khiến lần chạy sau luôn ghi đè lên file cũ không? *(Nếu có -> dung lượng không phình vô hạn, phải hạ xuống mức `INFO`)*.
4. **Tính năng lưu trữ hợp lệ:** Có phải file xuất ra `Downloads` / `Gallery` theo đúng chủ đích lưu trữ của người dùng không?

### Bước 2: CÔNG TỐ VIÊN (Defend — Bảo vệ cáo buộc Leak bằng Code)
Phản biện lại Bước 1 bằng chứng cứ dòng lệnh cụ thể:
- **Bẫy hàm xóa chết (Dead Cleanup):** Hàm xóa tìm thấy ở Bước 1 có thực sự được gọi trên luồng thực thi này không, hay chỉ là hàm không có caller / chỉ được gọi khi người dùng bấm Logout?
- **Lỗ hổng Exception / Coroutine Cancellation:** Dù Happy Path có xóa file ở cuối hàm hoặc ở `Worker`, nhưng nếu bước giữa ném `IOException` hoặc bị `CancellationException` (hoặc gọi hàm `suspend` trong `finally` mà thiếu `withContext(NonCancellable)`), file có bị bỏ rơi trước khi kịp tới lệnh xóa không? *(Nếu chỉ leak ở nhánh lỗi -> giữ lại Issue nhưng điều chỉnh về mức `WARNING`)*.
- **Bẫy Inode trên Linux/Android:** Dù có gọi `file.delete()`, stream mở file đó đã được đóng qua `.use {}` / `finally { close() }` chưa?

### Bước 3: THẨM PHÁN (Ra 1 trong 3 Phán quyết)
- **`UPHELD`:** Giữ nguyên 100% mức độ và nội dung của Vòng 1 (chỉ bổ sung thêm 1 dòng kết luận thẩm định).
- **`MODIFIED`:** Giữ lại Issue nhưng thay đổi mức độ rủi ro (`CRITICAL` <-> `WARNING` <-> `INFO`) HOẶC viết lại nội dung Issue cho khớp với nhánh lỗi thực tế sau khi tranh tụng.
- **`REJECTED`:** Bác bỏ hoàn toàn cáo buộc leak (chứng minh được file an toàn 100% kèm số dòng). Đẩy file xuống bảng `SAFE`.
